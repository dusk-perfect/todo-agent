# 改动同步清单

这份文档回答一个问题：**改了代码以后，还有哪些东西必须跟着改。**

先看清楚一共有多少份"对外的东西"——它们散在仓库内外，改一处漏一处，最容易被面试官当场问穿。

## 一、提交物清单

| #   | 东西                   | 在哪             | 怎么生成的                   | 谁会看                       |
| --- | ---------------------- | ---------------- | ---------------------------- | ---------------------------- |
| 1   | 代码                   | 本仓库           | 手写                         | 面试官会逐个文件读           |
| 2   | `README.md`            | 仓库根目录       | 手写                         | 先看这个，判断做没做完       |
| 3   | `SUBMIT.md`            | 仓库根目录       | 手写（提交说明正文）         | **主要评分材料**             |
| 4   | `GETTING_STARTED.md`   | 仓库根目录       | 手写                         | 要自己跑起来的人             |
| 5   | `server/openapi.yaml`  | 仓库             | 手写                         | 看接口契约                   |
| 6   | `docs/构建代码汇总.md` | 仓库             | `npm run docs:code` 自动生成 | 想快速看实现                 |
| 7   | `SUBMIT.docx`          | 仓库外的上级目录 | 与 #3 逐段一致               | 邮件附件                     |
| 8   | `SUBMIT.邮件版.md`     | 仓库外的上级目录 | 手写                         | 邮件正文                     |
| 9   | `智能体构建代码.md`    | 仓库外的上级目录 | 与 #6 完全一致               | 邮件附件                     |
| 10  | `submit.docx`          | 桌面             | 与 #3 逐段一致               | 邮件附件（真正发出去的那份） |

第 6 和第 9 是**自动生成**的，永远不会和代码对不上。第 3、7、10 三份是同一份内容的三个副本，段落必须逐字相同。第 4、5、8 是手写的，改代码时要人肉对照。

## 二、改了什么 → 要改哪里

| 改动的类型                                                 | 必须同步的地方                                                                                             |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 意图识别、规则、话术                                       | #2 README「实现说明」、#3 SUBMIT.md「功能列表 / 边界情况」、#4（若涉及操作步骤）、#6 #9（自动）、#3 #7 #10 |
| 动作类型（增删改）                                         | #3 SUBMIT.md（"九种动作"这类数量描述）、#5 openapi.yaml 若涉及字段、#6 #9                                  |
| 接口路径、请求字段、返回结构                               | #5 openapi.yaml、#2 README「接口一览」、#4 GETTING_STARTED「手动验证接口」、#6 #9                          |
| 扩展字段（priority / estimate / dueAt / dueTime / detail） | #5 openapi.yaml 的 Task schema、#2 README、#3 SUBMIT.md「扩展字段往哪存」                                  |
| 模型行为（提示词、超时、校验、降级）                       | #2 README「规则优先，模型兜底」、#3 SUBMIT.md「没有 API Key 的时候」                                       |
| 前端行为（界面、提醒、确认弹窗）                           | #2 README「产品化补充」、#3 SUBMIT.md 对应段、#6 #9                                                        |
| 数据目录、文件布局、环境变量                               | #2 README「环境变量 / 目录结构」、#4 GETTING_STARTED 同名章节                                              |
| 边界处理的增删                                             | #3 SUBMIT.md「边界情况」四类（指代 / 日期 / 输入 / 兜底）与「未做」                                        |

## 三、每次改完的标准动作

```sh
npm run docs:code      # 重新生成 docs/构建代码汇总.md（代码变了它就变）
npm run check:sync     # 跑一遍自动校验，列出没同步的地方
npm test && npm run typecheck && npm run lint && npm run fmt:check && npm run build
```

然后按校验脚本的提示，把缺的地方补上。`check:sync` 会检查：

- 生成文档里的代码块与源码是否逐字相同
- README 的接口一览 ↔ `openapi.yaml` ↔ `app.ts` / `tasks.ts` 里的真实路由
- 关键常量（匹配打分 0.93 / 0.95 / 0.5 / 0.05、模型超时 15 秒、不重试、模型名）在代码和文档里是否对得上
- 开发指南里列的文件是否都还存在
- 动作数量与 SUBMIT.md 里「九种动作」的说法是否一致
- 上级目录的 `SUBMIT.docx` ↔ 仓库 `SUBMIT.md` 是否逐段一致
- 上级目录的 `智能体构建代码.md` ↔ 仓库 `docs/构建代码汇总.md` 是否完全一致

校验脚本**查不了**的（要人眼过一遍）：

- 文档里的说法是否准确描述了行为，而不是只对上了数字
- 三份 `SUBMIT` 副本的语气与事实是否仍然成立
- 桌面的 `submit.docx` 是否已更新（它在仓库外，脚本默认不检查，跑 `node scripts/check-sync.mjs --docx <路径>` 指定）

## 四、三份 SUBMIT 副本怎么保持一致

`SUBMIT.md`（仓库）、`SUBMIT.docx`（上级目录）、`submit.docx`（桌面）是同一份内容的三个副本。

流程：以仓库 `SUBMIT.md` 为唯一真源 → 改 `SUBMIT.md` → 把同一段文字填进两个 docx → 跑 `check:sync` 确认逐段一致。

docx 里的排版（标题、加粗、小标题）不用重做，只改文字段落即可。
